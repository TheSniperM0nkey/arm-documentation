00 — Vision, Goals, and Principles

Who v3 is for. Single-admin homelab users — one person running ARM for their own household, explicitly not a shared service, multi-tenant platform, or commercial product. The user base skews toward data-hoarders, people who rip to preserve the raw bits rather than just to feed a streaming app. This single fact shapes real defaults: raw files are kept forever unless the user opts out, and re-transcoding from raw is treated as a first-class, expected operation rather than an edge case.

The two problems that justified a rebuild over a refactor:

  1. Resource isolation. In v2, rippers, UI, and transcoding all share one process tree inside a single container, so heavy work in one area degrades every other area — running multiple rips concurrently causes compute contention that the UI feels immediately. v3 must separate these so N concurrent rips and a transcode cannot starve the UI.
  2. Batch-rip resumability. A user who queues five discs and loses power mid-rip on disc #3 has, in v2, no way to recover — the system treats each rip as atomic and non-resumable. v3 must checkpoint finely enough that a power event doesn't discard completed work, with partially-completed work re-queued automatically on restart.

A third, adjacent pain point surfaced during scoping: users want Sessions — rip once, transcode many times with different presets. v2 conflates rip and transcode into one irreversible pipeline; v3 separates them.

Six design principles:

  1. Bits first, metadata second, transcode third. A rip succeeds the moment bits are safely on disk and recorded in the DB. Metadata enrichment and transcoding are independent downstream stages that can fail, retry, or be re-run without touching the raw.
  2. One service, one responsibility. The Ripper exists to turn a disc into bytes on disk. The Backend exists to own state and speak to the internet. The Transcode container exists to turn one raw into one output. The UI exists to render state and take commands. No service does "a little bit of the other guy's job."
  3. Backend is the single internet boundary. Ripper and Transcode containers never talk to the internet — all external calls (TMDB/OMDB/MusicBrainz/Apprise/webhooks) originate from the Backend. Workers are simpler to run (no API keys, no outbound firewall holes) and external credentials live in exactly one place.
  4. Postgres is the source of truth; stdout is the source of logs. Durable state lives in Postgres. Logs are structured JSON emitted to stdout and appended to a shared volume. No third persistence mechanism, no hiding debug data behind a query language.
  5. Crash-safe by default. Every long-running operation is checkpoint-able. A worker crash must not discard completed sub-work. A stale "in-progress" row with no live worker is the signal for "re-queue me."
  6. No sacred cows. This is a greenfield rebuild. Any assumption inherited from v2 is open for review — when in doubt, re-decide from first principles rather than preserve an old shape.

Success criteria for v3.0: five queued discs across two drives complete without manual intervention, including a simulated power-cut mid-batch that resumes cleanly; a ripped disc can have a new session applied from the UI months later without re-ripping; a single PR can change a protocol payload and its two endpoints (ripper side + backend side) atomically; a bug-reporter can download one log file scoped to one job_id and attach it to a GitHub issue; a fresh install on a new host lands at the login screen in under 5 minutes.

01 — System Architecture Overview

Container topology and service roles:

Service Image Lifetime Role
UI arm-ui Long-running SPA (Vite-built Vue 3) served by nginx; consumes Backend API + WS
Backend arm-backend Long-running FastAPI: job/session state machine, internet adapters, WS hub, spawns transcoders
Ripper arm-ripper Long-running, one per drive Bound to a single /dev/sr*; identifies disc, rips to /raw, reports to Backend
Transcode arm-transcode Ad-hoc, one per transcode Spawned by Backend; optional GPU pass-through; reports progress, exits
DB postgres:18 Long-running Source of truth for all state

The Backend is the brain; everything else is a worker that talks to it over REST + WebSocket.

Per-service detail:

  • arm-ui — stateless nginx + built SPA; proxies /api and /ws to the Backend; can be rebuilt/redeployed independently. Vue 3 (Composition API + <script setup>) with Pinia and vue-router.
  • arm-backend — Python 3.14 + FastAPI + Uvicorn + docker-py; not horizontally scalable in v3.0 (it owns the WS hub and state machine as a singleton); requires /var/run/docker.sock to spawn transcode containers.
  • arm-ripper-<drive> — one container per drive, created by the Backend on enrollment (not a static compose service); reads ARM_DRIVE_DEV at boot, registers with Backend, never talks to the internet.
  • arm-transcode-<uuid> — zero replicas at rest; Backend spawns one per transcode job, container exits on completion; auto-detects hardware encoders and advertises them at handshake; ARM_AUTO_TRANSCODE toggles "spawn when idle" vs. "user must initiate."
  • arm-db — postgres:18; bootstrap credentials via env, all other config (API keys, Apprise URLs) lives in DB rows written through the UI, stored plaintext.

Data flow, disc insertion to finished file (10 steps): (1) ripper detects insertion via 2s ioctl(CDROM_DRIVE_STATUS) polling — no host udev rules; (2) ripper scans with MakeMKV (track layout, volume label) or reads a MusicBrainz Disc ID for CDs; (3) ripper calls POST /api/ripper/identify, Backend queries TMDB/OMDB/MusicBrainz — on a hit the job becomes identified, on a miss it either blocks (default) or, in opt-in placeholder mode, rips immediately with identity deferred; (4) ripper creates one Track row per title and begins ripping, streaming progress over WS; (5) on completion the ripper emits rip.completed and ejects; (6) if the drive has a default_session_id and auto-transcode is on, Backend queues a session application; (7) Backend spawns arm-transcode-<uuid> via the Docker socket, mounting /raw read-only and /media read-write; (8) the worker runs HandBrake, streaming progress; (9) on completion it emits session.completed, exits, and notifications fire; (10) raw is retained by default — the user can queue additional sessions at any time.

Drive polling mechanics. The ripper reads disc presence via ioctl(CDROM_DRIVE_STATUS) — the same ioctl udev's cdrom_id helper uses, just without the event router, so it works inside a container with no host-side udev config. No root required (membership in cdrom suffices).

Value Constant Meaning
0 CDS_NO_INFO Drive does not report status (rare)
1 CDS_NO_DISC Tray closed, empty
2 CDS_TRAY_OPEN Tray out
3 CDS_DRIVE_NOT_READY Spinning up / reading TOC
4 CDS_DISC_OK Ready to read

Insert transition: NO_DISC/TRAY_OPEN → DRIVE_NOT_READY (1–5s) → DISC_OK, with DRIVE_NOT_READY treated as "keep polling," not an error. Polling is suspended once MakeMKV starts reading — a mid-rip eject shows up as a read error, not a status transition to race for; this also forecloses a v2-era bug (duplicate rip processes spawned by multiple insert events on the same device, since one long-running ripper now owns the drive and polling is gated on rip state). After completion the ripper auto-ejects and waits for the next DISC_OK; no state is held between discs, and each transition allocates a fresh job_id.

Shared volumes: arm_raw (/raw, rippers write / transcoders read, flat tree, no auto-prune), arm_media (/media, transcoders write, Plex/Jellyfin-friendly layout), arm_logs (/logs, all services write, JSONL correlated by job_id), arm_config (/config, Backend-written app config).

Privilege model. Backend mounts the Docker socket (treat as host-root-equivalent, a standard homelab pattern shared with Traefik/Watchtower). Rippers get device access. Transcode may get conditional GPU access. UI and DB are unprivileged.

Deliberately not in this architecture: a queue/broker (DB-as-queue for now, deferred decision — see doc 07) and a separate metadata worker (lookups stay inline in the Backend since latency is dominated by the MakeMKV scan anyway, and a separate worker is complexity without payoff at homelab scale).

02 — Job Lifecycle & Crash Recovery

This is the document behind the project's single biggest motivating goal.

The five entities. Job — one disc insertion, owns the overall rip outcome. Track — one logical piece of a disc (a title, a song, a data dump); this is the unit of checkpointing. Session Application — the durable record of "apply session S to job J," owning fan-out into Transcode Tasks. Transcode Task — the unit of work one arm-transcode container executes; one session application fans out to N tasks. Session — not itself a lifecycle entity, but a named, reusable bundle of (rip preset, transcode preset, output path template) scoped to a media type.

Job state machine: created → (identify OK) → identified → (first track begins) → ripping → ripped or ripped_partial (if some tracks failed). An identify failure detours to awaiting_user_id, from which the user resolving in the UI returns to identified. Terminal states: ripped, ripped_partial, abandoned (user gave up — also ejects the disc, though a stale abandon on a job that no longer owns the drive never touches the tray), failed (catastrophic identification failure).

Track state machine: queued → in_progress → done or failed. No stale state and no per-track claim — with one ripper container per drive, the ripper that creates the tracks is the only writer for the disc's lifetime, so nothing else can race for them.

Crash recovery — the core design decision: a rip restarts entirely from scratch on interruption, never resuming mid-track. Every track for the job resets to queued, /raw/<job_id>/ is wiped, and MakeMKV reruns — including tracks the DB had marked done. Three reasons: (1) MakeMKV can't resume a partial title, so the in-progress track was already forcing a re-rip; (2) a "done" file recorded in the DB may not have hit disk before a power cut, since there's no per-track fsync — trusting it risks silent corruption; (3) interruptions are rare, and re-ripping a few done tracks on an occasional power cut is cheaper than the durability machinery needed to make partial state trustworthy.

Two recovery paths trigger the reset, converging on the same DB transition: a Backend-startup sweep (finds every job stuck status='ripping' on boot — by definition all such jobs were interrupted — marks resumed_from_crash=true, resets tracks, increments attempts), and a ripper-startup probe (when a ripper container restarts and finds Backend reporting an in-flight job on its drive, it calls POST /api/ripper/jobs/{job_id}/resume, triggering the same reset). What this buys: a power cut mid-batch is fully recovered with no per-track timeouts to wait out; a ripper-only crash is handled by Docker's restart policy plus the startup probe; a Backend-only crash doesn't even interrupt rips, since rippers buffer their state-transition calls with exponential backoff (1s, 2s, 4s, 8s, 30s cap) until Backend returns. What it explicitly does not do: resume mid-track or mid-job (by design), or detect a hung-but-not-crashed ripper (no automatic timeout — the user restarts the container manually, which triggers the probe).

Session Application state machine: drafted → queued (normal path) → running → done / done_partial / failed. A special waiting_identify state exists for the case where a session is queued against a job still awaiting_user_id under a deferred-placeholder rip preset — the application parks there until identity resolves. Transcode Task state machine: queued → in_progress → (done | failed | stale) — unlike the rip side, this one genuinely needs per-task claims and heartbeats (claimed_by, claim_heartbeat_at), because multiple ephemeral transcoder containers really do compete for queued tasks. A stale claim requeues (re-transcode from scratch — HandBrake can't resume either), but already-done sibling tasks in the same application keep their output.

Why rip-level restart but task-level checkpointing for transcode — two different cost models. Rip-side: MakeMKV has no mid-title resume, "done" isn't guaranteed durable without a per-track fsync, and interruptions are rare enough that a wasted 30 minutes every few months is cheaper than the safety machinery. Transcode-side: a session application can fan out into many tasks, a 4-hour batch transcode losing all progress on a Backend restart is a much worse trade than a 45-minute rip losing progress on a power cut, and transcode tasks have stable inputs (raw files that don't change) and run in ephemeral containers that come and go anyway — a natural fit for claim-and-heartbeat with per-task retry.

Session model, in detail. Three tables recompose into one user-facing concept: rip_presets govern ripper behavior (track selection, identification mode, output mode), transcode_presets govern encoding (HandBrake preset reference, abcde profile, container, hardware preference), and sessions compose one of each plus an output_path_template. Built-ins ship locked (is_builtin=true, not editable through the API; the UI's "New Session" wizard can pre-fill from a built-in but always saves a new, unlinked row). Sessions are scoped to a single media type, and any session can be applied to any rip of the matching type — the UI filters the picker accordingly. Transcode preset is nullable (ISO/data-copy sessions skip transcode entirely). Sessions are re-runnable months later against an old rip, as long as the raw hasn't been pruned. Why the split: v2 bundled rip strategy + transcode settings + output convention into one concept, which can't cleanly express home-movie rips (no identification), ISO dumps (no transcode), or multiple output formats from the same source (MP3 + FLAC from one CD) — decomposing lets the parts be independently reusable while keeping the user-facing story simple ("pick a session").

Output paths and naming. /raw is internal, never exposed to media scanners, using MakeMKV's native title_tNN.mkv naming; cleanup removes the whole /raw/{job_id}/ directory once every derived transcode is terminal and retention policy allows (default keep_forever, matching the data-hoarder profile from doc 00). /media mirrors the Plex/Jellyfin convention (Movies/{Title} ({Year})/…, TV Shows/{Show} ({Year})/Season {NN}/…, Music/{Artist}/{Album}/…), with the top-level folder names configurable but the subtree shape fixed (changing it would break scanner matching). {transcode_slug} is included by default in filenames so the same raw rip transcoded multiple ways (1080p H.265, 4K HDR, phone-friendly) produces sibling files both Plex and Jellyfin group as alternate versions rather than colliding.

Filename templates apply at transcode time, not rip time — the rip step only ever produces MakeMKV's native /raw/{job_id}/title_tNN.mkv names. The guiding principle is "don't pretend to know what we don't know": MakeMKV surfaces only track layout and a volume label, no episode titles or season/disc numbers, so season and disc number for TV box sets are user-supplied, and there's deliberately no auto-SNNEMM guessing for TV — disc order isn't always episode order, and a wrong silent guess is worse than an honest mechanical name the user renames after the fact. "Play All" tracks aren't auto-detected either (duration-sum heuristics get confounded by bonus features on the same disc) — the ripper surfaces all tracks with durations at selection time and the user deselects what they don't want.

output_path_template tokens available depend on media type — {title}/{year} (movie), {show}/{season}/{disc} (TV, season/disc usually user-supplied), {track}/{duration_human} (from MakeMKV or CD), {artist}/{album}/{track_title} (from MusicBrainz/CD-Text — the one case ARM has reliable track-level metadata), {transcode_slug} (slugified transcode preset name, unavailable when there's no transcode preset), {ext}. Templates are validated on session save by expanding against a synthetic job and rejecting any template that would resolve a required slot to empty.

Concurrent write safety, two layers. The transcoder writes to <final>.arm-inprogress, fsyncs, then atomically rename(2)s to the final path — scanners never see half-written files, and a crash leaves orphaned .arm-inprogress files that the transcoder sweeps at startup. Separately, apply-time collision validation resolves every task's output path before fan-out and catches two cases: a cross-session collision (two sessions' templates resolving to the same path) and a cross-job collision (the same session applied to a job re-identified as a title already ripped) — both surface an explicit overwrite-or-cancel dialog rather than a silent auto-suffix, because auto-suffixing hides user intent and produces files neither scanner recognizes as meaningful versions. A DB-level partial unique index on transcode_tasks(output_path) for live-status rows is the safety net for anything the apply-time check missed. Applying the same (session, job) pair twice is idempotent — it returns the existing session application rather than fanning out twice.

Unidentified and placeholder rips. In opt-in placeholder mode (identification_mode=deferred_placeholder or global block_on_miss=false), ripping proceeds immediately on an identify miss, writing to /raw/<job_id>/ exactly as normal — nothing is ever renamed or moved as a consequence of identity resolution. Transcode is gated on identity, not rip completion: queued session applications sit in waiting_identify until the user resolves identity via POST /api/jobs/{job_id}/resolve, at which point Backend fans out transcode tasks against the now-resolved title with correct paths from the first byte written. If identity is changed again after transcoding has already started, already-completed outputs stay put — treated the same as a user manually renaming a movie post-transcode, out of scope for automatic cleanup.

03 — Protocol: REST + WebSocket Contract

Exactly two transports, nothing else. REST (HTTP/1.1, JSON) for anything that must durably land — config fetches, state transitions, CRUD. WebSocket for streaming only — live progress and async push. Direct DB access between services, file-based IPC, and shared memory are all explicitly out of scope; workers never read each other's state. All schemas are Pydantic models in packages/arm_common/schemas/, exported as OpenAPI from the Backend, imported by both producer and consumer sides so a protocol change is one PR touching both.

Base URLs. Backend listens on 8443 inside its container, TLS-only — there is no plaintext port. UI's nginx proxies /api/* and /ws/* to it; rippers and transcoders reach it directly on the compose network, verifying against the internal CA.

Service auth. Ripper and Transcode authenticate with a shared service token (Authorization: Bearer <token>), generated once at install and injected via Compose — no DB copy exists. The UI authenticates as a logged-in user via JWT on REST and a first-message {"op": "auth", "token": "…"} handshake on WS.

Ripper ↔ Backend REST surface (Ripper is the client, all under /api/ripper/): POST /register (startup handshake), GET /drives/{id}/config (rip parameters), POST /identify (blocks server-side during external lookup — body carries the MakeMKV scan or MusicBrainz Disc ID, response is the full Job row), GET /jobs/{id} (rarely needed, WS preferred), POST /jobs/{id}/tracks (create track rows post-identify), POST /jobs/{id}/resume (crash-recovery reset, described above), PATCH /tracks/{id}/complete and /fail, POST /jobs/{id}/complete. There is no ripper heartbeat endpoint — crash detection happens at container-restart time, not via timeout, and state-transition calls retry until acknowledged.

UI ↔ Backend REST surface (all under /api/): auth (login, logout — a no-op server-side since JWTs aren't tracked, password), config read/update, drives list/update, jobs list/detail/resolve/abandon, sessions CRUD, POST /jobs/{id}/transcode (queue a session), transcodes list/cancel, and logs (global query plus per-job JSONL view).

Transcode container ↔ Backend REST surface (minimal, short-lived client): POST /register, POST /tasks/{id}/claim, PATCH /tasks/{id}/heartbeat (every 30s), PATCH /tasks/{id}/complete and /fail.

WebSocket. One endpoint, /ws; clients subscribe to named topics after connecting. Topics: ripper.progress.{job_id} (per-track progress, fanned out from rippers), ripper.events (typed: started/completed/failed/needs_user_input/resumed_from_crash), transcode.progress.{task_id}, transcode.events (typed: session/task started/completed/failed), system.events (drive online/offline, backend restart, config change), logs.{job_id} (tails per-job log stream), ripper.commands.{drive_id} (Backend → the one owning ripper: identify.resolved, job.cancel), transcoder.commands.{task_id} (Backend → the one claiming transcoder: task.cancel). A publish op lets authorized principals push events the hub then fans out — a ripper can only publish to its own job's progress topic, never to typed-event topics, and the UI never publishes at all (backend code emits in-process instead). Progress topics are never persisted — writing every tick to the events table would multiply the write rate 10–100× for zero audit value, and the hub throttles progress to 1 Hz per (topic, track_id) regardless.

UI WS session scope. Opened after login, closed on logout/unload — the UI must not keep a WS alive in a background tab or service worker ("tell me what happened while I wasn't watching" is explicitly Apprise's job, not the UI's). There is no event replay or catch-up on reconnect; REST gives current state, WS gives live updates going forward, and that's the whole contract.

Why REST for state, WS for progress: state transitions must land (request/response acknowledgement, retry-until-acked, clean HTTP error codes on failure); progress is fire-and-forget telemetry where a dropped tick is invisible since the next tick replaces it, and one durable WS connection also carries identify-resolution events back to the ripper for free. No heartbeat protocol exists at all — crash detection is entirely container-restart-based, not timeout-based; the transcoder's REST claim/heartbeat is the one exception, because multiple ephemeral transcoders genuinely compete for tasks, a fundamentally different problem from the one-ripper-per-drive case.

Event envelope is uniform: {event_id, event_type, emitted_at, job_id, track_id, payload}, persisted to an events table that the Apprise-backed NotificationDispatcher consumes.

Versioning. URL-prefix versioning is reserved for a future break (v3.0 ships /api/ as implicit v1); arm_common schemas are semver'd with all services in a release pinned to the same version; fields are added freely within a major and never removed or renamed except across majors.

Deliberately excluded from the contract: inter-worker communication (rippers and transcoders never call each other — everything routes through Backend), Backend-initiated calls to rippers (Backend updates DB state and pushes a WS event instead; rippers are never HTTP servers), and binary transport (everything is JSON, unoptimized until measured).

04 — Data Model

Postgres 18 is the sole source of truth — no SQLite fallback, no sidecar store. Conventions: ULID primary keys prefixed by entity name (job_01HXYZ…) for legible logs and URLs; every table has created_at/updated_at; no soft-deletes (a status column hides a row if needed); foreign keys enforced at the DB layer; enums stored as plain VARCHAR rather than native Postgres types — a deliberate tradeoff, since ALTER TYPE is awkward in transactional migrations and some schema-diff tools gate enum-diff behind paid tiers, accepting that a bad value inserted via raw psql isn't caught by the DB itself (acceptable for a single-admin system).

Core tables:

  • users — one row per admin account; v3.0 seeds exactly one (admin, argon2id-hashed, password_must_change=true); the table exists so multi-user is trivial to add later without a migration.
  • config — a singleton row (sentinel id=1) holding third-party API keys, auto_transcode_on_idle, default_retention_policy, Apprise URLs, and the auto-generated session_signing_key used for JWT signing.
  • drives — one row per detected optical drive; enrolling one creates its ripper container. Carries status, rip_params_json, and a nullable default_session_id for auto-transcode.
  • jobs — one row per disc insertion. Carries disc_type, the state machine's status, resumed_from_crash, and forward-compatible-but-currently-unpopulated disc_fingerprint/disc_fingerprint_algo/aacs_disc_id columns reserved for a future community lookup database. The only index needed is (status), since the entire crash-recovery sweep is "find every job with status='ripping'."
  • tracks — the checkpoint unit. Carries kind, index, source_ref, status, attempts, output_path, sha256, plus forward-compatible label/role/role_source/edition columns for a future community-sourced disc database (free-text role, not an enum, so new values don't require schema changes). No claim/heartbeat columns — see the crash-recovery rationale in doc 02.
  • rip_presets — track_selection (main_feature/all_tracks/archive/custom), identification_mode (required/skip/deferred_placeholder), output_mode (tracks/iso/data_copy), track_filters_json for declarative rules. Built-ins are is_builtin=true and locked.
  • transcode_presets — tool (handbrake/abcde/none), preset_ref, container, hw_preference (null \= prefer HW/queue-if-busy/CPU-if-none, cpu_only, any), extra_args escape hatch.
  • sessions — the user-facing composition: name (unique per user), media_type, rip_preset_id, nullable transcode_preset_id, output_path_template, overrides_json.
  • transcode_tasks — one row per raw-track-to-output operation, the one table with real claimed_by/claim_heartbeat_at columns since ephemeral transcoders genuinely compete for work. A partial unique index on output_path for live-status rows is the DB-level collision safety net.
  • session_applications — the durable "apply session S to job J" record, including the waiting_identify status for placeholder-rip parking and an overwrite flag set by the collision dialog.
  • gpus — runtime hardware-encoder inventory, truncated and repopulated on every Backend boot (not persistent, not user-editable); tasks claim a row via SELECT … FOR UPDATE SKIP LOCKED and fall back to CPU automatically if the table is empty.
  • events — append-only typed-event log powering notifications and the UI activity feed, retained 90 days by default.

Schema and migrations. ORM is SQLModel (Pydantic + SQLAlchemy 2.0), one class per entity doubling as the wire schema where shapes match. Migrations run through Alembic --autogenerate, but generated revisions are explicitly treated as drafts — autogenerate handles column add/drop/type changes well but misses constraint renames, server defaults on existing columns, and partial-index changes, which get patched by hand. The Backend runs alembic upgrade head on startup before serving traffic; no sidecar migration container, no online schema changes planned (downtime during docker compose up after a migration is accepted for a homelab). Tortoise+Aerich and Piccolo were considered and rejected for weaker Postgres-specific feature support (partial indexes, JSONB ops, enum management).

Deliberately absent from the data model: a queue table (queue mechanism is deferred — "queue" is just rows WHERE status='queued' for now, keeping the door open to swap in Redis/NATS later without reshaping the model), per-user libraries (one library, one user), download/play-history tracking (ARM rips and transcodes, it isn't a media server), and disc rental/sharing.

05 — Cross-Cutting Concerns

Configuration is two-tier. Tier 1 (bootstrap, .env, sourced by Compose): POSTGRES_*, ARM_SERVICE_TOKEN (generated once, never rotated in normal operation), ARM_LOG_LEVEL, PUID/PGID (should match the media server's UID/GID), CDROM_GID (installer-detected). Tier 2 (runtime, DB): everything the user tweaks in the UI — API keys, retention, auto-transcode, Apprise URLs — stored plaintext in config, UI writes / Backend reads. No YAML files anywhere; the v2 arm.yaml pattern is retired.

Authentication, user-facing. Local users in users, argon2id-hashed. The seeded admin account gets a random first-boot password (not a fixed default) with password_must_change=true; the login response surfaces that flag and require_jwt 403s every endpoint except password-change/logout until it's cleared — so the well-known-default footgun v2 had is closed while still avoiding an operator lockout risk from a lost console printout. Auth is JWT, not cookie-based\: POST /api/auth/login returns {access_token, expires_at}, stored in localStorage, sent as Authorization: Bearer; WS auth is a first-message handshake with a 5-second window. Tokens are HS256-signed with config.session_signing_key (Backend is both issuer and verifier, so symmetric signing is fine), TTL 7 days, non-refreshing — one re-login per week, no refresh token, no MFA, all scoped explicitly to "single-user homelab." Logout is client-side only; there's no server-side blocklist, so an emergency "log out everywhere" means rotating the signing key. Why JWT over cookies: homelab operators deploy behind unpredictable reverse-proxy setups, and session cookies touch GDPR/CCPA consent law that Bearer-in-header sidesteps; single-user scope means cookie-specific wins (easy revocation, HttpOnly XSS protection) don't buy much anyway. Why argon2id over bcrypt: the 2015 Password Hashing Competition winner and current OWASP recommendation, memory-hard on three tunable axes versus bcrypt's single rounds parameter, no 72-byte silent truncation footgun, and the encoded hash self-describes its parameters so cost can be raised later via transparent rehash-on-verify.

Authentication, service-to-service. One shared long-lived service token in .env, injected into Backend/Ripper/Transcode, attached as Authorization: Bearer on REST and via the WS handshake. No per-service tokens — the shared-token tradeoff (a compromised ripper could present the same token as a different ripper) is accepted and mitigated at the authorization layer instead, since per-service token ceremony buys little on a private LAN with three or four containers.

Authorization rules, layered on top of the bearer check: drive-scoped ripper endpoints verify the referenced job's drive matches the caller's registered hostname; task-scoped transcoder endpoints verify the task is claimed by the caller; UI-only endpoints reject the service token and require a UI JWT; ripper/transcoder endpoints reject a UI JWT and require the service token. This closes "compromised ripper acts as a different ripper" down to "compromised ripper acts as itself" — the best an endpoint-layer check can do with a shared credential.

Transport: TLS everywhere, no exceptions, intra-compose and LAN-side alike — there is no plaintext internal hop, on the reasoning that "not reachable today" (the Docker bridge network) isn't the same guarantee as "not reachable ever" given a misconfigured port publish or a compromised sibling container. Deployment scope is explicitly LAN-only, never internet-exposed — remote access should go through WireGuard/Tailscale, not port-forwarding, which is also why Let's Encrypt is ruled out entirely (its HTTP-01 challenge needs public reachability the design deliberately doesn't have). An internal CA is generated once per install (~/arm/certs/, EC P-384, 10-year expiry, unique per install) with per-service leaf certs signed by it; the CA private key never leaves the host and is never mounted into a container. Postgres itself runs with ssl=on against the same CA, on the reasoning that the "compromised sibling sniffs a plaintext hop" threat model applies identically to DB traffic carrying credentials and secrets. Each container's entrypoint merges the mounted CA into the base image's trust store at startup (\~50ms), so the same trust store verifies both public outbound calls (TMDB) and internal HTTPS with no per-client verify= plumbing in application code. Deliberately not done: mTLS (the shared service token plus server-side TLS is judged sufficient without per-container client certs), auto-rotation (10-year expiry; install.sh --rotate-ca is the explicit, rare, confirmation-gated path), and public-CA-issued certs (no public CA fits a LAN-only design by construction).

WebSocket security, beyond the general auth model: a first-message auth window (5 seconds, anything else closes the connection with code 4401); origin validation against an allowlist (ARM_ALLOWED_ORIGINS) since browsers don't enforce same-origin on WS handshakes the way they do for XHR; per-topic authorization gated by principal type (UI-JWT principals can subscribe broadly, service-token ripper/transcoder principals only to their own command topic); JWT expiry is checked only at handshake, not enforced mid-connection (a long rip session outliving the 7-day token TTL just keeps working until the client reconnects); rate limiting is not enforced in v3.0, documented as an accepted gap at this scale.

Secrets (third-party API keys, Apprise URLs) are stored plaintext in config — DB dumps must be treated as sensitive — and are redacted from log lines via a structured-logging helper.

Logging. Structured JSON, one event per line, required fields including ts/level/service/job_id/track_id/session_application_id/msg (the job-context fields are null outside a job context, and must be populated inside one — this is what makes the per-job log view work). Emitted to stdout and appended to /logs/<service>.log with size-based rotation (10MB × 5 files, 50MB ceiling per service); a bug-report zip endpoint streams the per-job slice of every service's log. ARM_LOG_LEVEL=debug is set per-service via compose override with no UI toggle (restart-to-change is accepted). Deliberately not done: Loki/Promtail/ELK (gold-plated for this scale) and syslog/journald.

Observability beyond logs. v3.0 ships logs only — no Prometheus, no OpenTelemetry; the typed events table is the closest thing to metrics, SQL-queryable directly.

Code quality. One pre-commit stack gates all four Python packages equally: ruff (format + lint, replacing black/isort/flake8/bugbear/pyupgrade with one Rust-backed binary) and strict mypy (resolved against the real synced workspace via uv run, with every package shipping a py.typed marker so cross-package imports are trusted as typed).

Notifications run through Apprise with native pass-through URLs — users paste Apprise URLs directly into a UI textarea, with no ARM-side per-service dictionary to maintain. This directly reverses a v2 pain point: hand-maintaining a 30-service mapping went stale as new notification services (Signal, Home Assistant, MQTT, Pushover) piled up as feature requests. A MessageDispatcher fans typed events out to AppriseListener, BashListener (runs a hook script with declared inputs), and InboxListener (the UI bell). Event naming follows <domain>.<verb_past_tense> (e.g. rip.completed); the envelope shape is fixed, but the taxonomy of event types itself grows organically as features land.

06 — Deployment

Supported target: exactly one. Any Linux host running Docker Engine ≥ 24 and Compose v2 ≥ 2.20 — distro-agnostic, so this is the entire supported matrix. Explicitly not supported: Unraid/Synology/QNAP/other NAS-appliance GUIs (dropped 2026-06-05 — they run stock Docker so the generic path may work by accident, but it's untested), TrueNAS/iX Systems, Kubernetes/Helm, Docker Desktop on macOS/Windows for ripping (the VM boundary blocks internal SATA drive pass-through; USB may work via usbipd-win but is untested; NTFS bind mounts are unsupported since the translation layer ignores chown), and Podman (may work by accident).

Install layout, everything under a single prefix (~/arm/ by default, movable since all bind-mounts in the generated compose are relative): .env (0600), docker-compose.yml, certs/ (0700, including the never-mounted CA key at 0400), db/, raw/, media/, logs/. Nothing compiles on the host — the stack is entirely image-based.

Build chain. v3 images build fresh on upstream bases — no inherited v2 arm-dependencies image (that existed to bake HandBrake/MakeMKV/libdvd-pkg on a shared phusion base for the v2 all-in-one container; v3 splits those workloads so the shared layer isn't shared enough to justify a submodule) and no phusion/baseimage (adopted in v2 for multi-service supervision inside one container — irrelevant now that v3's topology is one process per container). Replacement bases: nginx:alpine for UI, python:3.14-slim-bookworm + tini for Backend/Ripper/Transcode. Dropping phusion removes a stack of v2 friction: the UID-unsettable limitation, start_udev.sh noise in bug reports, \~1GB base-image bloat, and the two-repo version-bump tax from submodule coupling. Hardened vendor bases (Chainguard, distroless, Bitnami Secure, UBI Micro) were considered and rejected — paid tiers gate the supply chain oddly for anonymous docker pull distribution, and free/distroless tiers have no shell, breaking the runtime CA-merge + PUID-remap pattern. Supply-chain hygiene is layered on top instead: digest-pinned base images (Renovate/Dependabot PRs on drift), SBOMs via syft + cosign attach sbom, Cosign-signed images via Sigstore's keyless OIDC flow, and weekly scheduled rebuilds so Debian security patches land without waiting for the next ARM release.

Compose topology. The generated compose references pinned images with no build: directives for end users; project name armv3 and armv3- container prefix guarantee zero collision with a coexisting v2 install. Rippers are not compose services — the backend scans /sys/class/block/sr* on boot, lists detected drives, and enrolling one from the UI creates a durable arm-ripper-<serial> container over the Docker socket (labeled arm.drive_id, restart: unless-stopped, with device_cgroup_rules letting the entrypoint pre-create device nodes itself rather than needing a static devices: bind — so it survives unplug/replug and renumbering). These containers sit outside the armv3 compose project namespace (docker compose down leaves them running; devtools/ripper-containers.sh manages them directly), and on every Backend boot the drives table is reconciled against labeled containers (missing → created, exited → started, orphan → removed). Transcode containers are likewise never declared in compose, spawned dynamically.

SCSI-generic pairing. MakeMKV enumerates via SG ioctls, not the block device, so each ripper needs both /dev/srN and its paired /dev/sgM — without it, makemkvcon info returns zero titles and the failure mode looks like "every disc is unidentifiable" rather than a clean error. The pairing isn't lexicographic (sr0 ≠ sg0 necessarily); the ripper's entrypoint now follows the kernel's own pairing at runtime rather than requiring it to be worked out at compose-authoring time.

Host-side auto-mount must be disabled on desktop hosts (GNOME/KDE/XFCE running udisks2+gvfs), because a host-side auto-mount holds the device exclusively enough that MakeMKV can still scan/rip via the SCSI-generic node but post-rip eject fails with "Device or resource busy." The installer writes a host-wide udev rule (UDISKS_AUTO=0 on all sr[0-9]* nodes) rather than scoping to a specific drive, since drives are hot-plugged and enrolled from the UI after install with no fixed drive list to scope to. UDISKS_AUTO=0 was chosen over UDISKS_IGNORE=1 specifically because the latter hides the drive from Files/Nautilus entirely, breaking the desktop user's ability to still browse it manually — the goal is skip-auto-mount, not hide-the-drive. DBus passthrough into the container was rejected (fails open on headless hosts with no session bus, fragile across distros); raw SCSI eject through /dev/sgM was rejected too (udisks2's PREVENT MEDIUM REMOVAL plus stale host mountpoints make it unreliable) — multiple other containerized-ripping projects hit the identical wall, and the host-udev approach is described as the converged industry pattern.

Why one ripper container per drive: one drive is one process is one crash domain — a failing ripper doesn't take its siblings down, each holds its own MakeMKV SCSI handle on its own device, and logs stay per-drive rather than interleaved.

Environment file. Generated by the installer with sensible defaults: POSTGRES_USER/PASSWORD/DB, ARM_SERVICE_TOKEN (openssl rand -hex 32), PUID/PGID (host user's), CDROM_GID (detected via stat -c %g /dev/sr0, else 44), ARM_LOG_LEVEL. Re-running the installer preserves .env and only re-derives host-dependent facts if they drifted.

File ownership uses the linuxserver.io-style PUID/PGID pattern. Each service's entrypoint starts as root, adjusts an internal user to match, then drops privileges before any filesystem write, so every byte ARM writes is owned by the configured UID/GID (matching, typically, the user's media server). Ripper and transcoder share PGID for group-writable handoff on /raw; output roots get the setgid bit on first boot so every subdirectory ARM creates inherits the parent group. The single biggest ownership rule: v3 never chown -R a user-mounted volume. If ownership is wrong at startup, the container logs a diagnostic and exits rather than mutating the mount — a direct reaction to real v2 data-loss bugs where recursive chown at startup clobbered user-owned Plex libraries and broke NFS mounts. Mismatched owners across /raw and /media (common when one is local disk and the other a NAS share) are meant to be reconciled at the mount layer (SMB uid=/gid=/forceuid/forcegid, or NFS idmapd/squash), not by asking the container to span two identities.

Privilege matrix: nothing runs --privileged; only arm-backend (Docker socket, root-equivalent, documented and accepted) and arm-ripper-* (device access, plus host optical GID via group_add) hold any elevated access, and even the ripper's device access is via ordinary devices:/group_add, not manual cgroup rules or a privileged flag.

Install steps, in order: prereq check (fails fast with a clear message) → create the prefix with correct permissions → generate the internal CA → probe for optical drives and issue leaf certs (backend/UI/DB always, plus one per detected drive) → seed .env with generated secrets (API keys left blank for the UI) → generate docker-compose.yml (installs fine with zero drives detected — just omits ripper services with a warning) → print next steps including where to find the generated admin password. install.sh --start runs docker compose up -d automatically; the default is "show me the commands first." Reruns are idempotent: .env and the CA are preserved, all leaf certs regenerate against the existing CA every run (harmless, self-healing, picks up SAN changes), newly-detected drives get new service blocks, and removed drives' blocks are left inert rather than auto-deleted.

Update, uninstall, backup. Minor upgrades are docker compose pull && up -d (Backend runs migrations forward — no downgrade path past minor versions, so back up the DB if paranoid); major upgrades rerun install.sh first to pick up new service blocks or cert SANs. Uninstall is docker compose down && rm -rf ~/arm — no systemd units, no other host state. Backup priority order: the CA private key (unique and unrecoverable, though losing it is merely annoying — rotate and re-import), a pg_dump (contains plaintext secrets, treat like a password export), .env (losing it just means regenerating tokens and matching the DB), and raw/media (the user's own responsibility, outside ARM's scope). docker-compose.yml itself is regeneratable and doesn't strictly need backing up.

07 — Open Questions & Deferred Decisions

Deliberately short — most first-draft open questions were resolved and folded into the main documents. The one live entry:

OQ-1: queue mechanism for async work. The data model already implements DB-as-queue via SELECT … FOR UPDATE SKIP LOCKED, and that's what v3.0 ships with. The deferred question is whether to eventually upgrade to Redis+RQ, NATS, or keep DB-as-queue indefinitely. Deferred because DB-as-queue is adequate for the expected scale (1–4 drives, 1–4 concurrent transcodes); the moment delayed jobs, fan-out topics, or back-pressure become a real need, it gets re-evaluated. The state machine is deliberately designed so the queue is a swappable component behind a JobQueue interface. Resolve-by condition: when a concrete pain point emerges (multi-minute claim latency, retry explosion), not on a calendar date.

The process for future OQs: when ready to resolve, fold the decision directly into the relevant architecture doc in a PR that also deletes the OQ entry — no separate resolutions/ archive, since git history carries the context. OQs never block development; services are designed around their plug-in points from the start.

08 — v2 Isolation and Cutover Plan

The isolation rule, stated exactly: "No v3 PR modifies a v2 file. Every v3 artifact is an addition under v3/. The only PR that modifies v2 files is the cutover PR, and it does so exactly once." Every file at repo root as of the start of v3 development — the v2 Python package, its Dockerfile, devtools/, setup//scripts/, test/, the arm-dependencies submodule, arm_wiki/, and every root-level config/doc file — stays byte-identical throughout v3 development. The one permitted root-level change is additive .gitignore rules, and even that's normally avoided since v3's own .gitignore lives nested under v3/. Inside v3/, anything goes — its own code, compose file, tooling, tests, docs, gitignore.

Coexistence on one host during development relies entirely on namespacing: compose project arm vs armv3, container prefix arm-* vs armv3-*, volume prefix arm_* vs armv3_*, UI port 8080 vs 8081, DB port/engine entirely different (MySQL vs Postgres). The one shared resource that can't be namespaced away is the physical optical drive — both stacks can map /dev/sr0, but only one should actively use it; the documented pattern is to stop v2's ripper service before exercising a real v3 rip, and start it back up after.

CI workaround. GitHub Actions only reads .github/workflows/ at the repo root, so v3 CI can't literally live under v3/.github/. The compromise: v2's existing workflow files stay untouched, and v3 adds new files named .github/workflows/v3-*.yml, each scoped via a paths: filter to v3/** so it only fires on v3 changes — this is the one deliberate exception to "everything v3 lives under v3/," justified because adding new files isn't modifying existing ones.

Branching. v3 development runs on a long-lived v3/main branch, with feature branches targeting it; the repo's actual default branch (main) keeps receiving v2 fixes if any occur but receives nothing from v3 until cutover.

The cutover PR, step by step (exactly one PR ever modifies v2 files): (1) move v3's tracked contents to root via git mv — services, packages, docs/arch and friends, devtools, compose files, install.sh, pyproject.toml — with several files staged under temporary names to avoid collision until v2 is removed; (2) retire v2 — git rm the v2 package, Dockerfile, devtools, setup/scripts, test/, dependency files, and deinit the arm-dependencies submodule, while explicitly keeping LICENSE, CODE_OF_CONDUCT.md, SECURITY.md, CONTRIBUTING.md (to be rewritten), VERSION (to be bumped), the existing docs/ PSDs/API-key guides, arm_wiki/, and GitHub issue-template/dependabot/PR-template files; (3) finalize the v3 files at root by renaming out of their temporary staged names; (4) rewrite user-facing docs — swap in the v3 README, add a v3.0.0 CHANGELOG entry, rewrite CONTRIBUTING for v3's workflow, bump VERSION to 3.0.0; (5) retire v2's CI workflows and drop the v3- prefix from the v3 ones now that they're the only workflows (re-evaluating whether repo-automation workflows like stale.yml/greetings.yml are still wanted before deleting them); (6) ports stay as-is — UI keeps 8081 rather than reclaiming v2's 8080, since the already-installed, TLS-secured deployment is the source of truth; (7) v2 is preserved with no git tag — it remains reachable via ordinary pre-cutover git history (git checkout <sha>) and via its already-published, untouched Docker image tags, so a user who wants to stay on v2 simply keeps running their existing image.

What the cutover explicitly is NOT: not a data migration (v2 users opt into v3 by pointing at a fresh database and re-ripping, or stay on the pinned v2 tag); not a branch rename (main stays main, its content just pivots); not a soft/gradual migration (v2 is removed from main in one PR — the git history and existing images are the preservation mechanism, not a parallel branch kept around).

Readiness criteria for cutover (the cutover PR only runs once all are met): every architecture decision in this directory is resolved or explicitly deferred with a known plug-in point; a fresh-host install via the one-liner lands at the login screen, accepts a disc, and produces a transcoded file using the Big Buck Bunny ISO fixture; the crash-recovery exercise passes (five queued rips + simulated power cut mid-batch resumes cleanly, unattended); at least one real Blu-ray, DVD, and audio CD rip have each completed end-to-end on a contributor's machine; CI is green on main and the full stack runs end-to-end on the single supported target; and maintainers have agreed v3 is ready to replace v2.

09 — Testing Philosophy (as-built)

Records what was actually built, as of 2026-05-16, which diverged from the original plan in doc 05 — that plan's testing section was retired in favor of this dedicated document once the Backend's tiers settled differently than first specified.

Five principles. (1) Tests run with one command and zero infrastructure — uv run pytest, no Docker/Postgres/drives/network; the moment a suite needs a sidecar to pass, it stops being run. (2) Coverage is a floor for confidence, not a vanity number — the Backend holds 100% statement coverage (branch coverage measured, not gated), with any excluded line requiring an explicit, written justification rather than a lowered bar. (3) Test the real code path, fake only the true I/O boundary — the DB session, the Docker socket, outbound HTTP, the WS hub, the filesystem clock are faked; a test that mocks the thing it's testing gets deleted. (4) Speed is a feature — the 600+-test Backend suite runs in \~15s, with deliberately-slow production paths (argon2 work factor) dialled down in tests without changing the algorithm or code path itself. (5) Determinism over fidelity where they conflict — a test that passes or fails based on whether the host happens to have a GPU or Docker socket is worse than no test; environment-dependent startup code is pinned to one deterministic branch and the other side gets a unit test or an explicit, justified exclusion instead.

Two tiers, as actually built for the Backend (diverging from the original "per-service unit tests against real Postgres + contract tests" plan):

  • Tier 1 — fast fake-session tests, the bulk of the suite. Each test builds a minimal FastAPI app (or calls a function directly) and overrides the DB-session dependency with an in-memory fake AsyncSession that pattern-matches select(...).where(...) against seeded rows — a deliberate, owned piece of infrastructure, not a generic mock framework. \~0.3s per test; this is where exhaustive router/logic branch coverage lives. When a handler needs a query shape the fake can't express (e.g. Postgres-specific ON CONFLICT), that's treated as a signal that the SQL belongs to the integration tier, not a reason to force the fake to cover it.
  • Tier 2 — real-DB e2e harness, booting the actual arm_backend.main:app (real lifespan, real seeders, every router mounted, real JWT loading a real user row) against a real SQLAlchemy engine on file-backed SQLite. This is the only tier exercising main.py, db.py, seeders.py, and the wiring the fake-session tier structurally can't reach. SQLite stands in for Postgres because "zero infrastructure" outranks dialect fidelity for API-surface coverage — the production models' JSONB/ARRAY types are swapped for generic JSON in this harness, and the explicit, accepted consequence is that Postgres-only dialect features and real Alembic migration fidelity are out of scope for this tier.

Why not real Postgres in CI: it was the original Tier-1 design and was abandoned because it violates the zero-infrastructure principle for the 99% of tests that don't need real Postgres semantics — every contributor and CI run would pay container-startup latency and flakiness to test routing logic that doesn't care what the database is. The paths that do care are deliberately pushed to a separate, explicitly-scoped integration tier instead.

Coverage policy. 100% statements on the Backend, branch coverage measured but not gated (coverage report runs in CI but there's no fail_under — a deliberate choice, with a regression ratchet ready to enable later but declined for now so coverage noise doesn't block unrelated PRs). Exclusions require an explicit, justified # pragma: no cover comment on the line above the excluded statement, reserved for genuinely unreachable-in-process code (the real DB session, the uvicorn entrypoint, lifespan shutdown-timeout arms, post-seeder impossible states, dead-by-construction fallbacks) — never for code that's merely hard to reach, which stays documented as a residual gap instead of hidden behind a pragma.

What's explicitly not tested, and why: real Postgres dialect + Alembic migrations (deferred to the not-yet-built integration tier); cross-service flows over real REST/WS between live containers (the planned-but-unbuilt contract tier's job); browser e2e/Playwright (fragile, low return for a thin UI reviewed visually plus vitest unit tests); and real hardware — real drives, GPUs, MakeMKV/HandBrake against arbitrary discs (GPU/Docker probing is pinned deterministic in tests; the planned Big Buck Bunny loop-device rig is meant to cover real-pipeline assertions).

Planned but not yet built: a contract tier checking the published OpenAPI against arm_common.schemas on every PR (catching "schema changed, generated client didn't"), plus one contract test per ripper/transcoder call posted against a spun-up Backend in test mode (catching "producer changed, consumer didn't"); and a Big Buck Bunny integration rig — a devtools/arm-test-rip-style script mounting a CC-BY-licensed BBB ISO as a loop device in a disposable ripper container, meant to be the home for real-pipeline and real-Postgres-dialect assertions the SQLite e2e tier explicitly skips. Arbitrary proprietary discs are never used in testing, for obvious legal reasons.

Sharp edges worth knowing: the Backend's Settings object is a process singleton whose test-time env defaults are set by tests/e2e/conftest.py importing first and winning session-wide — new shared env defaults must go through that lens; test module basenames must stay globally unique across services because pytest's default import mode aborts whole-suite collection on a duplicate; db._build_engine mangles sqlite:// URLs via a urlparse round-trip, so the e2e harness swaps the engine object post-import rather than relying on the import-time DATABASE_URL; long inline # pragma comments get reflowed by ruff onto the wrong physical line, breaking coverage's recognition of them, so the justification belongs on the line above, not inline; and argon2 cost is dialled down in the e2e harness specifically (the hash self-describes its params, so a cheap hasher still round-trips the real verifier) to cut an \~80s run to \~15s.

10 — ISO-Source Ripping (proposed, design only)

The one document in this set explicitly marked not built — a design written and reviewed before any code, with open decisions still collected at the end.

The name clash to avoid. "ISO" means two unrelated things: ISO as output (rip_presets.output_mode='iso', already shipped — a full-disc image produced from a physical disc) and ISO as source (ripping from an existing .iso file through the normal pipeline, no physical disc involved) — this document is exclusively about the second, always called "ISO-source ripping" or "ISO ingestion" to keep the two straight.

The shape, in one sentence. An ISO-source ripper is an ephemeral, backend-spawned worker container — the transcode-container lifecycle, not a long-running service. The Backend spawns one per ISO on demand, it rips, reports, and exits (auto_remove); it is explicitly not a persistent arm-ripper-iso daemon, and the eventual front door (UI file upload → spawn a worker per upload) is deferred, with only the ephemeral-spawn architecture being locked in now.

Why now. ISO-source ripping already half-exists, but only as an internal test hook: the ripper accepts ARM_MANUAL_TRIGGER_ISO, treats the ISO as its bound device, rips once on startup, then idles forever — the opposite of ephemeral — with no API, no UI, and no spawn mechanism, which is why devtools/iso-smoke.sh had to grow into a large hand-rolled orchestrator (fixture fetch, key scrape, manual docker run assembly, live-ripper stop/restart, polling, teardown) just to exercise it. The good news is the Backend already spawns ephemeral workers exactly this way for transcoding — ISO ingestion is proposed as the same mechanism pointed at a different image, reusing two things nearly verbatim: the disc pipeline itself (already source-blind — the scan layer already routes iso:<path> vs dev:<path>, and everything downstream of scan is untouched) and the transcode dispatcher's spawn/claim/heartbeat/stale-sweep pattern, cloned with a new rip_tasks table pointed at the ripper image instead.

Target architecture. A rip_tasks table mirrors transcode_tasks (status, claimed_by, claim_heartbeat_at, attempts, plus source_ref and session_id); a rip dispatcher background loop — a near-copy of the existing transcode dispatcher's spawn logic — counts in-progress tasks against MAX_PARALLEL_ISO_RIPS, dequeues queued rows FIFO with FOR UPDATE SKIP LOCKED, spawns one ephemeral ripper per task with a unique hostname and label, and runs a stale-claim sweep that doubles as this feature's entire crash-recovery story (replacing the physical ripper's boot-probe mechanism). The ripper gains a third entry mode alongside "poll a physical drive" and the legacy one-shot env var: given ARM_RIP_TASK_ID, it claims the task via the same handshake pattern transcoders use, runs the existing rip pipeline unmodified, and on completion marks the task terminal and exits — no idle-forever, no WS command loop. There's deliberately no new WS command for this; the dispatcher-spawn handshake replaces it, with WS retained only for in-flight cancel (mirroring transcode cancel).

The one genuine new wrinkle: drive identity. Transcoders never create jobs and so need no drive, but ISO rippers do — Job.drive_id is a non-null foreign key. Two options were weighed: (A), recommended for v1 — the backend creates an ephemeral Drive row per spawn (hostname arm-ripper-iso-{suffix}, device_path \= the ISO reference), hands its ID back at claim time, and a kind discriminator (optical | iso) hides these from the UI's live-drive list; this keeps the pipeline and owner-auth model byte-identical, which is judged the biggest practical win. (B) — decoupling via a nullable Job.drive_id plus a Job.source field — is cleaner long-term but touches drive-owner auth, get_in_flight_job, and the whole rip-start/track/complete path, so it's deferred as a bigger, later change if ephemeral drive rows become noisy.

Source today vs. tomorrow. v1 is a server-side library directory — a host path bind-mounted read-only into each spawned worker at /isos, enumerated via a new GET /api/iso/library endpoint for the UI picker. Browser upload is explicitly deferred (multi-GB resumable upload, staging storage, and garbage collection are called out as the real remaining work) — but the proposal is explicit that the ephemeral-spawn core doesn't change when upload lands; uploads are just a new way to populate the same library.

Backend and Ripper changes summarized. New endpoints: POST /api/iso/rips (enqueues a task; enforces path containment via realpath resolution against the library root — described as the feature's single most important security property, since an absolute or arbitrary client-supplied path must never be accepted), GET /api/iso/library, the worker claim/heartbeat handshake cloned from the transcoder's, plus cancel (force-stopping the labeled container). The Docker socket is already mounted into the Backend for transcode spawns, so no new privilege is taken on. On the ripper side: a task-mode entrypoint keyed off ARM_RIP_TASK_ID; an auth model matching the transcoder's (token-only, no per-container leaf cert — sidestepping the problem of issuing a stable cert to an inherently unstable ephemeral worker); and log identity taken from an explicit service name rather than derived from a device path, so each spawn logs uniquely with zero collision.

What disappears if this ships: the "pause the enrolled drive's managed container" dance the smoke script currently does (unnecessary once ephemeral workers have unique hostnames and never touch a real /dev/sr* node); the idle-forever container and its bespoke docker run block; and an earlier considered "compose-overlay" idea, rejected on the grounds that an ephemeral worker isn't a compose service any more than the transcoder is — it ships as an image plus backend settings.

Concurrency falls out of the dispatcher pattern for free — natural parallelism, one container per task, capped by MAX_PARALLEL_ISO_RIPS (default 1, matching transcode's default), queued FIFO. This is noted as the first real consumer of the still-deferred general "queue mechanism" question from doc 07.

Six decisions still needed, each with a stated recommendation: drive identity (option A above, recommended), whether to reuse the existing ripper image with a task-mode command or build a dedicated arm-ripper-iso image (reuse, recommended), whether to clone the rip_tasks/transcode_tasks pattern directly or build a generalized worker_tasks abstraction over both (clone, recommended), how the ISO library catalog is enumerated (backend scans a mounted directory, recommended), cancel semantics (label-based force-stop matching transcode, recommended), and the default MAX_PARALLEL_ISO_RIPS value (1 to match transcode, though ripping is I/O-bound rather than GPU-bound so a higher default is arguably cheaper).

Migration path. devtools/iso-smoke.sh collapses under this design to a thin client: drop a fixture in the library, POST /api/iso/rips, wait for the job, optionally assert on the downstream transcode — with the fixture-fetch and MakeMKV-key-resolution helpers kept as genuine test scaffolding, and the manual docker run block, live-ripper stop/restart dance, and idle container all retired. ARM_MANUAL_TRIGGER_ISO itself is slated for retirement unless a no-backend single-container smoke test is still wanted for some other purpose.

How the Eleven Documents Fit Together

Document 00 sets the why; 01 sets the what (topology). Documents 02, 03, and 04 form the operational core — lifecycle, wire contract, and schema — and reference each other constantly (a session's output-path template defined conceptually in 02 is a literal column in 04, resolved over the REST calls specified in 03). Documents 05 and 06 are the non-functional backbone every service is built against regardless of feature — auth, TLS, logging, and code quality on one side, deployable packaging and file-ownership rules on the other. Document 07 is the deliberately short record of what's still genuinely undecided. Document 08 governs the meta-process of shipping this entire rebuild without breaking the existing v2 release its users depend on today. Document 09 documents engineering practice as it was actually built — explicitly superseding the original testing plan sketched inside document 05. And document 10 is the one forward-looking proposal in the set, clearly labeled as design-only and not yet real, reusing the exact ephemeral-worker pattern document 01 established for transcoding rather than inventing a new one.
